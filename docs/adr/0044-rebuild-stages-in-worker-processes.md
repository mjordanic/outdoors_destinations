# Rebuild stages run their independent work in forked worker processes

The Europe rebuild ran each stage on one core for about 29 hours. Most of that time goes to work whose units do not depend on each other: a chunk of vertices or TrailGraph Segments sampled from rasters, a chunk of hikes measured for the similarity facts, a pair of walks checked for Twins. `dayhike.parallel` maps such units over worker processes, and `sample-dem`, `sample-landcover`, `sample-trailgraph` and `build-similarity` take `--workers N` (or `DAYHIKE_WORKERS`). The default is 1: today's serial build, in one process.

The workers are forked from the stage's process, so they read what the stage already holds (the amenity trees, the TrailGraph's search arrays, the rasters' paths) without copying them over a pipe; only the units and their results cross. Results come back in unit order and are combined exactly as before (a Twin group's root is its first row whatever order the pairs are checked in), so the files are the same with any worker count. Everything that writes, and everything whose result depends on what came before (joining Twin groups, the order of the facts), stays in the stage's own process. Each worker opens its own SQLite connections and raster datasets; none is shared across a fork.

**Considered Options**: split the snapshot by country or region and merge the Catalogs (hikes, node networks and Twins cross borders, so the merge would not equal one build); a spawned or forkserver pool (every worker would load its own copy of what the stage holds, and ingest's snapshot is several GB on Europe); threads (the work is Python, held by the GIL). Rejected.

**Consequences**: fork is used explicitly, also on macOS, where Python's default is spawn; a worker never uses a connection or dataset its parent opened. On macOS numpy's BLAS is Apple Accelerate, whose GCD threads a forked child cannot use (a worker's BLAS call hung for good in 6 of 6 test runs): importing dayhike sets `VECLIB_MAXIMUM_THREADS=1` before numpy loads, which keeps every BLAS call on its caller's thread, and more than one worker is refused in a process that loaded numpy before that could take effect. Copy-on-write pages the workers touch cost memory, so the worker count is chosen for the machine: on Europe each worker adds part of the stage's own memory, not all of it. `ingest` (its relation DayHikes, DayStages, NetworkHikes and their Twin checks, GeometryStore rows), `sample-climate` and `export-serving` still run in one process, whatever `DAYHIKE_WORKERS` says: ingest's process holds the most memory (8.4 GB on Europe), so running it in workers waits for a later change with its own memory budget.
