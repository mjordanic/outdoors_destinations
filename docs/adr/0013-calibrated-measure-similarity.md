# Similarity is a Hiker-weighted mean of calibrated Measures

The Hiker says what "similar" means for one query by weighting each Measure 0–100 (0, or leaving it out, excludes it). There are 26 Measures, one per fact: length, elevation gain, Difficulty, highest and lowest point, ProfileShape, LandCover mix, Peak summited, Viewpoint along, Peaks around, temperature, precipitation, solar radiation, SolarAspect southness, WaterSource count, DryStretch, the five facilities flags, SurfaceMix, TarmacApproach, RoundTrip, ClimbGrade and SteepestKm. There are no Facets: a theme of several Measures is just several weights.

Raw Measure scores live on different scales. A random pair of DayHikes scores 0.6 or more on the ProfileShape nine times in ten, but rarely on length. So each raw score is calibrated before it is weighted: it becomes the share of random DayHike pairs that score lower on that Measure, ties counting half (the mid-rank empirical CDF). The similarity of two DayHikes is Σ wⱼ·cⱼ / Σ wⱼ over the weighted Measures both can be scored on; a missing Measure drops out and the rest renormalize. With several Seeds a candidate's similarity is its best Seed's. Ties break on the same mean of raw scores, then on DayHike id. The score shown is that similarity's share among stored random pairs under the same weights, raised to the number of Seeds, so 0.5 reads as a typical random pair and 1.0 as better than every stored pair; it does not change the order.

`build-similarity` computes the facts of every Catalog DayHike once from the Catalog, the GeometryStore and FABDEM (ADR-0006: Ranking still never reads the GeometryStore). It stores them beside the Catalog in `{catalog}.similarity/` as memory-mapped float32 numpy arrays, with the Calibration: 1,024 quantiles per Measure and per QueryMonth variant of the three climate Measures from 100,000 random pairs, and the raw scores of 20,000 of those pairs on every Measure for the shown score. A query scores the Seeds against every DayHike with numpy and calibrates with `searchsorted`; nothing is rebuilt per request. Ingest and every sample step that changes the Catalog delete the directory, so the facts must be rebuilt after them; the Calibration alone (`--calibrate-only`) after a Measure constant changes. A missing directory, a version hash of the constants and the Catalog's DayHike ids are checked at load, so stale facts fail instead of ranking wrongly.

A query can be restricted to a set of DayHike ids, so a DriveTime pre-filter can run before Ranking; the post-filter `filter_by_drive_time` is unchanged.

**Considered Options**: keep Facets and calibrate FacetScores (a Facet's mean already narrows the spread, and the Hiker asked to weight individual Measures); z-score or min-max per Measure (fixes location and scale but not shape: the ProfileShape stays skewed, yes/no flags stay atoms, z-scores are unbounded); rank the candidates of each query per Measure (amplifies tiny differences inside a narrow DriveTime pool and costs a sort per Measure per query); a separate calibration per Seed (the score then means "best available", not "alike"); probability calibration or learned weights (needs Hiker ratings; `labels` is empty); leave yes/no Measures uncalibrated (a flag would pull twice as hard as a continuous Measure at the same weight); store the facts in the Catalog SQLite (row-wise reads per query, and the Catalog stays derived facts from ingest). Rejected.

**Consequences**: a perfect match on yes/no Measures calibrates below 1 (agreeing on a common value is weak evidence), so a similarity near 1 needs continuous Measures; the shown score anchors the reading. Correlated Measures (length with DryStretch, highest point with temperature) still double-count when both are weighted. The Calibration depends on the population: it must be rebuilt when the Catalog's DayHikes change.
